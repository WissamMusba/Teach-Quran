 REVISION BLOCK (latest build) — SYNC OVERHAUL + LAZY DRAWINGS + 10px PADDING
 Added: Wed Aug 05 2026. Supersedes the V1 sync description further below.
================================================================================

WHAT CHANGED IN THIS BUILD
  1. Fixed the sync layer end-to-end:
     - ROOT BUG FIXED — addToSyncQueue (localDB.ts) inserted into a column
       `retryCount` that does NOT exist in sync_queue (real columns: synced,
       attempts). Every call threw, so: manifests/bookmarks/lastRead were NEVER
       queued, the pendingChanges badge never incremented, AND pullRemote threw
       on every pull with a newer cloud manifest (app showed "offline"). Now uses
       INSERT ... ON CONFLICT DO UPDATE SET synced=0. Payloads, meanwhile, are
       re-read from the cache rows — only the queue row's existence matters.
     - PULL LOOP FIXED — pull-side writes no longer re-dirty the queue:
       saveChunkNoQueue + saveManifestLocal(..., queue=false) +
       saveAudioNotesRange(..., queue=false). Before, every download re-queued
       the row so the next push re-pushed it -> infinite ping-pong.
     - VERSIONING MADE DETERMINISTIC — no more FieldValue.increment anywhere.
       Each doc carries an explicit v. After a successful push the LOCAL manifest
       mirror is rewritten to the pushed v + serverTs (queue=false), so the next
       pull sees cloud.v === local.v and skips. No drift loops.
     - saveStudentData no longer hardcodes drawing chunk v=1 (was resetting the
       version counter, causing re-downloads of the device's OWN chunks).
     - flushPendingSave (QuranViewScreen) dropped its redundant addToSyncQueue
       call (double-write) so addPendingChange() finally fires -> badge works.
     - MANUAL SYNC NOW TESTS FULL PUSH+PULL — DashboardScreen handleManualSync
       always runs processSyncQueue({ pull: true }) (no longer blocked at
       pendingChanges===0), reports "Pushed: N | Pulled: M", and the header
       Sync button disables only while in flight.
     - FIRST READ INCLUDES STUDENTS — pullRemote caches the students list via
       cacheStudentList so Dashboard reads offline-capable on first launch.

  2. WHAT SYNCES vs WHAT DOESN'T: synced = bookmarks, lastRead (reading
     position + mark), highlights (mistakes are derived from them), text notes,
     audio-note registry. Drawings DO NOT sync via the main queue.

  3. CLOUD LAYOUT (per student):
       students/{sid}/meta/overview ... bookmarks + lastRead + pages.{k}.v map
       students/{sid}/draws/{k} ......... annotations chunk (highlights+notes,
                                          NO strokes) for canvasKey page_N/surah_N
       students/{sid}/audioNotes/{r} .... 10-page audio-note registry doc
       students/{sid}/drawings/{r|sN} ... LAZY drawing chunk (compacted +
                                          content-box-normalized, per 10-page
                                          range or per-surah)

  4. AUDIO NOTES — 10-PAGE RANGES: metadata now stored per range
     (audio_notes_cache table; key r_{lo}_{lo+9} or s_{surah} fallback), pushed
     ONE doc per range, pulled as ONE read (< 1MB) ONLY when the range is not
     local. registerAudioNote(..., page?) gets the page when known. Legacy
     manifest entries are migrated by migrateLegacyAudioNotes(). The m4a files
     + playAudioNote are UNTOUCHED.

  5. LAZY DRAWINGS: queue rows are handled for chunks/manifest/audio only.
     Drawing strokes stay in SQLite as raw canvas coords. On canvas save,
     pushDrawings(studentId, groupKey, pageKeys, geo) compacts (thin points to
     >= ~3px + simplify epsilon 1.5, 4-decimal rounding) and normalizes each
     point to a fraction of the TEXT CONTENT BOX = pageWidth - 2*hPad, marking
     paths norm:1. On page open, pullDrawings() denormalizes back to the CURRENT
     screen's content box (padX = hPadFor) and only fills pages with NO local
     strokes (never clobbers). Legacy raw cloud paths without the norm marker
     pass through untouched.

  6. DRAWING WEIGHT: capture now samples points (3px min gap for the pen,
     coordinates rounded) in DrawingCanvas via lastPenPointRef; eraser stays
     dense; underline unchanged. compactStroke uses thinStrokePoints(3) +
     simplifyStroke(1.5).

  7. 10px LEFT/RIGHT PADDING ON PHONE: MushafPageView hPad (pageWidth < 600)
     changed 8 -> 10 so mushaf text never touches screen edges; tablets keep 8%.
     hPadFor() in src/utils/stroke.ts mirrors this (w>=600 ? w*0.08 : 10) so the
     drawing normalizer/denormalizer and the page renderer agree.

KEY FUNCTIONS (new/changed)
  - src/api/sync.ts
      requestSync({pull?})/processSyncQueue alias — single-flight; returns
        {success, pushed, pulled}.
      pushAllDirty — 3 push sub-passes: annotations chunks (draws/{k}, strokes
        stripped, explicit v), manifest (overview, merge), audio ranges
        (audioNotes/{r}). Clears queue row per key, mirrors local manifest v.
      pullRemote — downloads overview when cloud.v > local.v, downloads newer
        annot. chunks (merging local strokes back in), pulls missing/newer audio
        ranges, caches the students list.
      pushDrawings/pullDrawings/pullAudioRange — lazy, fire-and-forget, guarded

  - src/database/localDB.ts
      rangeKeyForPage/rangeKeyForVerse/getVersePageDB/getAudioNotesRange/
      saveAudioNotesRange/getAllAudioRanges/migrateLegacyAudioNotes —
        the 10-page audio registry + legacy manifest migration.
      saveChunk(..., queue=true)/saveChunkNoQueue — pull writes never re-queue.
      saveManifestLocal(..., serverTs, queue) — manifest pull mirror no-queue.
      saveStudentData — drawings saved with cur.v+1 and queue=false.
  - src/utils/stroke.ts — hPadFor + content-box compactStroke/denormalizeStroke.
  - src/screens/QuranViewScreen.tsx — load effect now raw-pass-through + lazy
    pullDrawings/pullAudioRange for the current range; onSave fires the lazy
    pushDrawings; flushPendingSave fixed; handleVoiceNoteSaved passes the page.
  - src/components/drawing/DrawingCanvas.tsx — pen capture thinning + rounding.
  - src/components/quran/MushafPageView.tsx — hPad phone 8 -> 10.
  - src/screens/DashboardScreen.tsx — manual sync always push+pull, count alert.

KNOWN GAPS (accepted for now)
  - Concurrent two-device edits to the same chunk merge last-write-wins at doc
    level (version skew possible); no server timestamps for conflict intent.
  - Drawing pull only fills pages with zero local strokes; explicit "restore"
    of an already-drawn page is not offered.
  - sync_queue still has ONE row per (studentId, canvasKey); the badge counts
    queued payload keys, not individual edits.

 SECTION 0 — DEMO: THE SYNC PIPELINE (how the format works)
================================================================================
This demo documents the full sync feature: edit -> SQLite -> Firebase, its
triggers in App.tsx/DashboardScreen, and its UI status in syncSlice. All later
sections (1-10) use exactly this format.

--------------------------------------------------------------------------------
### FILE: src/api/sync.ts
ROLE: Push-only sync engine: reads dirty students from SQLite, uploads each
      student's monolithic blob to Firestore, clears the queue on success.
IMPORTS: firestore, getUserId (./firebase); getPendingSyncStudents,
         clearSyncQueueForStudent, getStudentData (../database/localDB)
DEPENDS ON: src/api/firebase.ts (auth state), src/database/localDB.ts
            (sync_queue + student_data_cache tables)
USED BY: App.tsx (initial/interval/AppState triggers), DashboardScreen.tsx
         (manual sync on focus)

#### serverNow()
WHAT: Firestore server timestamp helper with a client-clock fallback.
FLOW: Try firestore.FieldValue.serverTimestamp(); if unavailable, return an
      ISO string. Blends server and client clocks (see NOTES).
CALLS: (firestore).FieldValue.serverTimestamp -> authoritative write time
CALLED BY: processSyncQueue (self, inline)
AFFECTS: Firestore write field updatedAt (used by nothing today — display only)
NOTES: [v1] Mixed timestamp types (Timestamp vs string) make ordering
       unreliable. [v4] replaced by FieldValue.increment monotonic counters.

#### processSyncQueue(): Promise<{success, synced?, failed?, error?}>
WHAT: Main entry point of the ENTIRE sync feature. Called from 4 triggers.
FLOW: 1) getUserId() -> bail if logged out.
      2) getPendingSyncStudents() -> distinct dirty studentIds from
         sync_queue WHERE synced=0. Empty -> success(0).
      3) For each dirty student: getStudentData(sid) -> full blob from
         student_data_cache (the ENTIRE student: bookmarks, highlights,
         drawings, notes, lastRead). Missing -> clear queue row, continue.
      4) firestore set() of the whole blob at
         users/{uid}/students/{sid}/data/studentData with merge:true.
      5) clearSyncQueueForStudent(sid) -> delete queue row. Count synced.
      6) Per-student catch -> count failed, leave queue row dirty (retry
         next trigger).
CALLS: getUserId -> auth guard
       getPendingSyncStudents -> dirty student list (localDB.ts:71)
       getStudentData -> local blob to upload (localDB.ts:34)
       firestore().collection(...).set() -> cloud write (merge)
       clearSyncQueueForStudent -> queue cleanup (localDB.ts:80)
CALLED BY: App.tsx:35 (initial sync after auth)
           App.tsx:43 (30-min interval, SYNC_INTERVAL)
           App.tsx:51 (AppState change active<->background)
           DashboardScreen.tsx:45 (manual sync on screen focus)
AFFECTS: Cloud: users/{uid}/students/{sid}/data/studentData (overwritten).
         Local: sync_queue rows deleted on success (synced state lost — no
         history). UI: syncSlice.setSyncing/setSynced/setOffline drive the
         SyncStatus/SyncIndicator components.
NOTES: [v1 LIMITATION] Blob is 400KB-1.3MB; >1MB documents FAIL SILENTLY in
       Firestore (student data silently lost). No pull (second device never
       receives data). Audio note paths reference local files only.
       [v4] whole file replaced by per-canvas push + pull
       (SYNC_OPTIMIZATION.txt §5.5).

--------------------------------------------------------------------------------
### FILE: src/database/localDB.ts  (sync-related surface only)
ROLE: SQLite layer: local source of truth for students, mushaf pages, and
      the sync queue. Every table and accessor lives here.
DEPENDS ON: react-native-sqlite-storage, @react-native-firebase/auth
USED BY: src/api/sync.ts, src/api/student.ts, src/screens/QuranViewScreen.tsx,
         src/screens/DashboardScreen.tsx, src/components/quran/MushafPageView.tsx

#### getStudentData(studentId)
WHAT: Read one student's entire blob (JSON) from student_data_cache.
CALLS: getDB().executeSql SELECT data ... WHERE studentId=?
CALLED BY: sync.ts:23 (upload source), QuranViewScreen.tsx:220 (hydrate
           Redux studentSlice on student select)
AFFECTS: Feeds studentSlice.studentData -> every screen that renders
         highlights/bookmarks/notes/drawings (QuranView, Mistakes, Notes,
         Bookmarks).
NOTES: [v1] single blob column. [v4] replaced by per-canvas rows
       (student_data_cache: studentId+canvasKey).

#### persistStudentData(studentId, data)  [private]
WHAT: Atomic SQLite transaction: upsert student blob + insert/replace a dirty
      sync_queue row (data column '{}' — payload lives in the blob row).
FLOW: transaction -> INSERT OR REPLACE student_data_cache; INSERT OR REPLACE
      sync_queue(studentId, '{}', synced=0).
CALLS: getDB().transaction
CALLED BY: saveStudentData, addToSyncQueue (both just delegate here)
AFFECTS: student_data_cache + sync_queue rows; making a student "dirty" is
         what processSyncQueue() later picks up.
NOTES: sync_queue.data is ALWAYS '{}' — the real payload is re-read from
       student_data_cache at push time. Deleting one table without the other
       breaks the pipeline.

#### saveStudentData(studentId, data)
WHAT: Public alias for persistStudentData. Called on every student edit.
CALLED BY: QuranViewScreen.tsx:248 (flushPendingSave, debounced 400ms)
AFFECTS: Marks student dirty -> next sync trigger pushes.
NOTES: [v4] signature changes to per-canvas saveChunk.

#### addToSyncQueue(studentId, data)
WHAT: Public alias for persistStudentData — v1 compat name.
CALLED BY: QuranViewScreen.tsx:248 (immediately after saveStudentData)
AFFECTS: Same as saveStudentData (it is the same call).
NOTES: v1 redundancy kept for API stability; [v4] becomes a no-op.

#### getPendingSyncStudents(): Promise<string[]>
WHAT: DISTINCT dirty studentIds (sync_queue WHERE synced=0) — the sync
      engine's work list.
CALLED BY: sync.ts:17 (processSyncQueue)
AFFECTS: Controls which students get uploaded.
NOTES: [v4] replaced by getDirtyCanvasesByStudent (per-canvas granularity).

#### clearSyncQueueForStudent(studentId)
WHAT: Delete all queue rows for a student (called after successful upload).
CALLED BY: sync.ts:30 (success), sync.ts:24 (stale local data)
AFFECTS: Removes the student from the dirty set; failure to clear would
         re-upload forever.

#### getPendingSyncQueue() / markQueueItemsSynced(ids)
WHAT: Legacy row-level queue API (row IDs, synced flag UPDATE).
CALLED BY: (nothing in src/ today — kept for compat)
NOTES: Superseded by getPendingSyncStudents + clearSyncQueueForStudent.
       Safe to delete in rebuild.

#### purgeLocalStudent(studentId)
WHAT: Deletes BOTH student_data_cache row and sync_queue rows for a student.
CALLED BY: src/api/student.ts deleteStudent flow (verify)
AFFECTS: Local copy of a student; next pull would re-create from cloud.

--------------------------------------------------------------------------------
### FILE: src/store/syncSlice.ts
ROLE: Redux state for sync status UI (syncing / last synced / offline).
USED BY: App.tsx, DashboardScreen.tsx, src/components/sync/SyncIndicator.tsx,
         src/components/common/SyncStatus.tsx

#### setSyncing / setSynced(timestamp) / setOffline
WHAT: Three actions marking sync lifecycle transitions.
CALLED BY: App.tsx:34/42/51, DashboardScreen.tsx:45 (wrap every
           processSyncQueue() call)
AFFECTS: SyncIndicator + SyncStatus render states ("Syncing…",
         "Synced 2m ago", "Offline"). Any screen showing sync status depends
         on these actions staying paired with processSyncQueue calls.

--------------------------------------------------------------------------------
### FILE: App.tsx  (sync triggers only — full doc in Section 1)
ROLE: App shell: Redux Provider, PersistGate, NavigationContainer, and the
      global sync scheduler.
#### AppInner effect (lines 31-56)
WHAT: Registers the 3 recurring sync triggers, once authenticated.
FLOW: initialSync() on mount -> 30-min setInterval -> AppState change
      listener (fire on every active<->background transition).
CALLS: processSyncQueue (src/api/sync.ts) at :35, :43, :51
       setSyncing/setSynced/setOffline (syncSlice)
AFFECTS: If you change the sync entry point (e.g. [v4] requestSync), all 3
         call sites must be updated together.
NOTES: AppState listener fires on BOTH enter-background and re-enter-active;
       duplicate pushes possible (min-interval guard added in [v4]).

--------------------------------------------------------------------------------
FEATURE MAP — SYNC PIPELINE
  Edit in QuranViewScreen ──┐
    updateData() ──────────┼─► flushPendingSave (400ms debounce)
    saveStudentData ───────┤   └─► persistStudentData
    addToSyncQueue ────────┘       └─► SQLite: student_data_cache + sync_queue
                                      └─(dirty flag)► processSyncQueue (4 triggers)
                                      └─► getPendingSyncStudents ► getStudentData
                                      └─► firestore set() ► clearSyncQueueForStudent
                                      └─► syncSlice: Syncing/Synced/Offline
                                      └─► UI: SyncIndicator + SyncStatus
  If you change localDB tables (student_data_cache/sync_queue) you MUST update
  sync.ts + student.ts + QuranViewScreen flush in the same change set.

#### useEffect sync scheduler (App.tsx:31-56)
WHAT: Runs three global sync triggers while the user is authenticated.
FLOW:
1. Early-return when !isAuthenticated (App.tsx:32) — no timers, no listeners.
2. TRIGGER #1 — initialSync() immediately on effect run (33-39): dispatch(setSyncing)
   -> await processSyncQueue() -> on success dispatch(setSynced(ISO-now)) (36),
   on failure dispatch(setOffline()) (37).
3. TRIGGER #2 — setInterval(..., SYNC_INTERVAL) fires the same routine every 30 min
   (41-46); note setSynced(now) here passes a timestamp (44).
4. TRIGGER #3 — AppState.addEventListener('change') (48-53): an IIFE sync runs on
   every transition between 'active' and any other state (background/foreground
   edges, App.tsx:50-51).
5. Cleanup (55): clearInterval + sub.remove() — runs when isAuthenticated flips or
   AppInner unmounts.
CALLS:
- dispatch(setSyncing) -> sets sync.status='syncing' (syncSlice.ts:5)
- processSyncQueue -> pushes queued SQLite rows to Firestore (sync.ts:12)
- dispatch(setSynced) -> status='synced', pendingChanges=0 (syncSlice.ts:6)
- dispatch(setOffline) -> status='offline' (syncSlice.ts:7)
CALLED BY: (top-level effect inside AppInner render)
AFFECTS: redux `sync` state (status, pendingChanges); Firestore
         users/{uid}/students/{sid}/data/studentData (via processSyncQueue);
         SQLite sync_queue table (cleared per student in sync.ts:30).
NOTES:
- setSynced() at App.tsx:51 omits the timestamp arg used elsewhere (36, 44) — the
  `syncedAt` field is never set anywhere, so any UI relying on it would be stale.
- Sync runs are fire-and-forget; an in-flight promise resolving after unmount still
  dispatches (harmless with redux, but double-syncs possible at app-state edges).
- No sync when logged out: DashboardScreen is the only other sync caller.

#### getStudents(): Promise<{success, students? | error?}>
WHAT: Returns the student list for the current user — instantly from SQLite
      cache when available (with background refresh), else from Firestore.
FLOW: 1) getUserId() guard.
      2) getCachedStudentList() (localDB.ts:86, keyed by uid).
      3) Cache hit -> fire refreshInBackground(uid) (NOT awaited), return
         cached immediately.
      4) Cache miss -> firestore students collection orderBy('createdAt',
         'desc').get(); map docs to {id, ...data}; cacheStudentList();
         return.
      5) Catch: re-read cache; return it if present, else
         { success:false, error }.
CALLS: getUserId -> auth guard (firebase.ts:5)
       getCachedStudentList -> SQLite student_list_cache (localDB.ts:86)
       refreshInBackground -> background cache refresh (self)

       cacheStudentList -> SQLite student_list_cache upsert (localDB.ts:95)
CALLED BY: DashboardScreen.tsx:30 (mount effect) -> dispatch(setStudents)
           (studentSlice.ts:6) on success.
AFFECTS: Redux: student.list via caller's setStudents.
         Local: student_list_cache (both branches write on fresh fetch).
         UI: Dashboard FlatList; offline first launch with no cache shows
         error (AlertModal via showAlert is NOT called here — the effect
         silently drops failures).
NOTES: refreshInBackground updates SQLite but NOT Redux, so the in-memory
       list can be stale until remount. orderBy('createdAt') is a simple
       single-field index (no composite index needed). Empty cloud list
       results in an empty cache — a legitimately-empty account is cached
       as [] and the catch-branch cache check (`length > 0`) then treats
       [] as "no cache", forcing a cloud read every launch (minor).

#### initDatabase()
WHAT: Idempotent one-time DB bootstrap: opens quran.db (WAL mode) and creates
      every table, the sync_queue dedup + UNIQUE index, and the verses indexes.
FLOW: 1) Guard: if dbInstance set, return (module-level singleton).
      2) SQLite.openDatabase('quran.db', location 'default').
      3) PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL.
      4) CREATE TABLE IF NOT EXISTS, in order:
         - surahs           (id PK, name, englishName, verses)            :13
         - verses           (id autoincrement PK, surahId, verseNumber,
                             textArabic, textIndopak, textTranslation,
                             page)                                        :14
         - student_data_cache (studentId TEXT PK, data TEXT blob)         :15
         - sync_queue       (id autoincrement PK, studentId, data,
                             synced BOOLEAN DEFAULT 0)                    :16
         - mushaf_pages        (pageNumber PK, data TEXT JSON)            :17
         - mushaf_pages_indopak(pageNumber PK, data TEXT JSON)            :18
         - student_list_cache  (uid TEXT PK, students TEXT, updatedAt)    :19
         - page_layout_cache   (pageNumber, textStyle, headerVisible, fs,
                                sparse, screenW, lines;
                                composite PK of all six key columns)      :20-24
      5) Legacy cleanup: DELETE FROM sync_queue WHERE id NOT IN
         (SELECT MIN(id) ... GROUP BY studentId) — keeps the OLDEST row per
         student, collapsing duplicate pre-dedup rows                       :26
      6) CREATE UNIQUE INDEX idx_sync_queue_student ON sync_queue(studentId)
         — enforces one queue row per student, matches the INSERT OR REPLACE
         semantics of persistStudentData                                   :27
      7) CREATE INDEX idx_verses_surah ON verses(surahId)                  :28
         CREATE INDEX idx_verses_page  ON verses(page)                     :29
CALLS: SQLite.openDatabase, executeSql (native)
CALLED BY: downloadAndCacheQuran (src/database/quranData.ts:96) — the ONLY
           caller in src/. DB init therefore happens lazily on first Quran
           download, i.e. through SplashScreen.tsx:17.
AFFECTS: ALL tables. Nothing reads/writes SQLite before this runs; every other
         helper (getDB()-based) assumes it already completed.
NOTES:
  - No index on verses(surahId, verseNumber) composite — getVersePage's
    `WHERE surahId=? AND verseNumber=?` (quranData.ts:197) relies on the
    surahId index alone + LIMIT 1. Fine at 6236 rows, worth a composite index
    in rebuild.
  - The dedup DELETE at :26 runs on EVERY app start, not once. With the
    UNIQUE index + INSERT OR REPLACE flow (max 1 row/student) it is a no-op on
    fresh data, but on legacy multi-row queues it keeps MIN(id) = the OLDEST
    row: if the oldest is synced=1 and a newer row is synced=0, the dirty row
    is deleted and the student stops syncing.
  - No `PRAGMA foreign_keys`; verses.surahId has no FK constraint (surprise:
    surahs and verses are not linked, only by convention).
  - page_layout_cache holds 604 pages x (6 key cols) x 15 lines — grows with
    every font-size/width change; only cleared in a 7-page range by
    clearPageLayoutCacheRange, never wholesale.

#### getPageLayoutCache(pageNumber, textStyle, headerVisible, fs, sparse, screenW)

     — both run the same persistStudentData (identical INSERT OR REPLACE of the
     same two rows). Redundant work per flush (:327).
  2. Stale-snapshot clobbering: any two edits within 400ms lose the first (both
     dispatch from the same closure snapshot; pendingSaveRef keeps only the
     latest). Rapid word toggles drop highlights.
  3. sync_queue is one-row-per-student (UNIQUE index localDB.ts:27) — payloads
     overwrite, so the sync badge counts edits, not queued snapshots.
  4. lastRead restore effect depends ONLY on lastRead.surah (:311) — changing
     verse within the same surah never re-scrolls.
  5. Continuous-mode scroll restore uses magic y=idx*45 (:236,:308) — wrong for
     wrapped text.

     module-level playing/playToken state goes stale.
  7. isIndopak also matches 'indopak'/'harmattan' (:113) which are absent from
     quranSlice's textStyle union — reachable only via `as any` from Settings.
  8. PanGestureHandler disabled in page mode (:513) — horizontal surah-swipe
     code (:428-431) is dead in page mode by design.
  9. Side-effect-in-render in SpreadItem (:46-47) and single-mode renderItem
     (:580-581) — guarded by promise refs, still impure.
  10. loadSurah's surahIdRef guard (:258) + pageScrollSurahChangeRef (:267-270,

      navigation together.
